## 时间接口

- 输入是带 `Z` 或明确数字偏移的 UTC 日期。归一化后以同一时刻供各模型取用。历史正闰秒的 `:60` 要保留在可解析的 UTC 标签中。现有界面用数值毫秒驱动，略过该标签。JSON 的 `jdUtcQuasi` 是能表达不同日长的两部分 UTC 日期。
- `jdTai` 与 `jdTt` 为两部分儒略日。TT 比 TAI 快 32.184 秒。截断月球位置是采用 TT 的候选路径。`jdTdb` 是给八大行星根数、轨道线以及日后适当的 IAU 姿态模型的动力学时刻。同一帧的位置和轨道线取同一个历元。计算两时刻差时，先对各自的两部分求差再相加。旧 `years` 接口仅是 `JD_START` 起算的 365.25 日年。
- UT1 用于地球自转和地面观测。本包 `jdUt1` 为 `null`。将来需从有版本的 IERS 地球定向数据取得 `UT1−UTC`，高精度站点还需极移和相关姿态数据。其他卫星拟合的原始输入时标待核实。旧 `spinW` 内有 **69.184 秒**的固定补偿，未来直接使用 TDB 时须复核该项，避免重复补偿。快档视觉自转仍使用画面帧时长。 [USNO 时标说明](https://aa.usno.navy.mil/downloads/Circular_179.pdf) · [固定源码核查](model-timescale-audit.md)
- 闰秒资料固定为 IERS Bulletin C 72，适用起点为 1972-01-01。`2027-06-28T00:00:00Z` 起的预览记录标记 `assumed-no-new-leaps`，沿用最后已知的 `TAI−UTC = 37 s`。未来若新增闰秒，实际时刻会按净新增秒数变化。固定原型默认拒绝表外 UTC，预览需明确选择该假设。 [IERS Bulletin C 72](https://datacenter.iers.org/data/html/bulletinc-072.html)

`positions[].sampleKeyNumericJD` 是旧档案的配对键。旧模型输入是 UTC 锚定的数值 JD，Horizons 样本是 `TIME_TYPE=UT` 的历史查询，ERFA `clock.samples` 则是独立时标基准。三者保留各自历元。以项目历元为例，旧画面标签是 `2026-11-01T16:00:00Z`，同数值 JD 的 Horizons 回显是 `16:00:00.0029`。`horizons.jdTdb` 来自 Horizons 的 UTC 与时间差字段，保留原档案精度。需要同一物理时刻的误差测量时，先核对历元，不能直接按数字键认定时标对齐。 [固定 M2-2 时间与参考架证据](horizons-time-frame-report.md)

## 位置、参考中心与姿态

所有向量以公里保存，采用右手 J2000 黄道 XYZ。+X 指 J2000 春分点方向，+Z 指黄道北极，+Y 由 `X × Y = Z` 确定。Horizons 从 ICRF 绕 X 轴使用 84381.448 角秒的固定黄赤交角，输出几何位置。SOL 旧结果使用其声明的 J2000 黄道近似，月球向量的参考架实现仍有待独立验证。 [Horizons 参考架说明](https://ssd.jpl.nasa.gov/horizons/manual.html#reference-frames)

| 对象 | 固定 SOL 输出 | 独立 Horizons 参考 |
|---|---|---|
| 太阳 | `sun`，日心零向量 | `10` 是太阳中心，零点按定义给出 |
| 地球 | `earth` 槽计算近似地月质心，旧画面将它当作地球 | `emb` 是 `3 / 10`，`earth` 是真实地心 `399 / 10` |
| 月球 | `moonRelativeEarth` 是月球模型的地心向量，`moon` 是旧 `earth` 槽与该向量的和 | `moon-earth` 是 `301 / 399`，`moon-sun` 是 `301 / 10` |
| 木星 | `jupiter` 是系统质心近似 | `jupiter-system` 是 `5 / 10`，`jupiter-body` 是本体中心 `599 / 10` |

上表的数对为「目标编号 / 原点编号」。局部场景以同一来源、同一物理时刻、同一参考架的母行星中心为原点。日心月心减真实地心应闭合到独立月球地心向量。本包闭合残差最大为 `7.446e-8 km`，低于原 M2-2 的 `1e-5 km` 门槛。旧模型则按旧混合中心逐位闭合。地月质量关系及修正方案见 M3-A，交接包未重跑候选实验。 [固定 M3-A 报告](m3a-report.md)

- **显示接口**　读入 `xyz` 为 binary64，带上来源、目标、中心、参考架、历元和单位。物理计算保留 km，AU 换算使用 `1 AU = 149597870.7 km`。在渲染边界先以双精度计算 `目标位置 − 场景原点`，再映射引擎轴与缩放为场景单位，最后转渲染精度。太阳系总览、近景及模型半径可有独立显示设置，科学数据保持原单位。轨道顶点与天体在同一局部场景使用同一个平移和轴变换。
- **局部姿态接口**　位置平移后仍用惯性轴。确需天体固连坐标时，另提供 `target`、`bodyFixedFrame`、`inertialFrame`、`epoch`、`rotationBodyToInertial` 和 `provenance`。旋转约定为 3×3 行序矩阵乘列向量，逆变换用转置。引擎若更改轴序或手性，应分别变换输入与输出基底。JSON 的 `attitude` 为 `null`，月球和其他卫星姿态、地表经纬与可见性须另验。模型显示可另有视觉朝向。

例子使用项目历元的 `horizons.vectors['moon-earth']`，得到 `[-220946.676708, 299073.414492, 11287.229048] km`。若演示用右手 Y 向上，取轴变换 `(x, z, −y)` 及每单位 `1000 km`，局部显示位置约为 `[-220.946677, 11.287229, -299.073414]`。这是导入示例，引擎未选定轴约定或场景比例。

## 离线复验

```powershell
node scripts/science/verify-m3-portable.mjs
node scripts/science/verify-m3-portable.mjs --git
node scripts/science/verify-m3-portable.mjs --replay
```

- 第一条只读 JSON。复制脚本和 JSON 到任意保留这两条相对路径的目录，即可在无 Git 仓库、无项目依赖和无网络时检查中心、时标和 binary64 位模式。
- `--git` 通过固定提交的 Git 对象重建交接包，使用固定 Horizons 解析器检查 6 组响应、8 个原始日期、参考系与摘要。复跑固定时间原型，对 9 个 ERFA 时刻采用原 100 微秒门槛，并检查固定拒绝边界。过程在临时目录内执行。
- `--replay` 在此基础上以固定 M1 捕获脚本、原始源码 blob 和已存在的 TypeScript 5.9.3 复验原始 **8 个日期、360 个向量分量**。三种命令都不写入现有基线。`--capture` 只用于首次创建，存在文件时拒绝覆盖。

JSON 用 UTF-8、标准十进制数字与有符号位模式字符串。跨语言导入应把位置读成 binary64。`float64HexBE` 是从 IEEE 754 双精度值按 8 字节大端读取的 16 位十六进制字符串。Python 可用 `struct.pack('>d', value).hex()` 检查，不需要天文或渲染依赖。

本次三种复验均通过。另在无 Git 仓库和项目依赖的临时目录仅用脚本与 JSON 复跑，并用 Python 标准库独立校验 45 个旧向量分量、三次月球中心闭合、9 个时标及上面的局部坐标示例。交接 JSON 的 SHA-256 为 `2ae993fbaa43c5f0604590b2304f62486e71158a2d15a8aa2a66c24dbbf1d1c5`。
